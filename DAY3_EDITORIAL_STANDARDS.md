# Day 3 Editorial Standards Rulebook — Workflow-First Content System

## 1) Editorial mission

### What this site helps readers do
Help solo operators build reliable software-enabled operating systems so they can deliver client work consistently, reduce admin overhead, and make better tool decisions with less risk.

### What makes this editorial approach useful
- It translates tool decisions into workflow outcomes.
- It prioritizes implementation over opinion.
- It gives readers a clear “what to do next” on every page.
- It is scoped to solo and micro-team constraints (time, budget, complexity tolerance).

### What “workflow-first” means in real editorial decisions
- We publish pages only when tied to a specific operational process.
- We evaluate software by workflow fit, not feature volume.
- We frame recommendations with constraints, tradeoffs, and setup effort.
- We connect strategy pages to execution assets (templates/checklists).

### What this site refuses to become
- A generic “best software” list factory.
- A broad business motivation blog.
- A high-volume AI content farm publishing shallow pages.
- An affiliate-first site where monetization replaces usefulness.

## 2) Content quality standard

## Publication gate: every page must do all 5

1. **Solve one clear reader job-to-be-done.**
2. **Offer an actionable decision or implementation path.**
3. **Add unique value beyond vendor docs and generic blogs.**
4. **Fit a defined search intent and page role in site architecture.**
5. **Link to and from the right adjacent pages (no content islands).**

### Minimum usefulness requirements
- Gives at least one concrete next action.
- Reduces confusion by narrowing choices with criteria.
- Includes practical constraints (budget, complexity, maintenance load).
- Helps the reader avoid a common workflow failure mode.

### Minimum specificity requirements
- Defines who the advice is for (business type/stage).
- Names the context (which workflow stage/process).
- Includes “choose X when / avoid X when” guidance.
- Uses real scenario framing, not abstract claims.

### Minimum originality requirements
- Has an opinionated point of view tied to this audience.
- Contains a unique framework, checklist, matrix, or decision logic.
- Avoids reworded consensus content.

### Minimum structure/readability requirements
- Strong intro with intent match and outcomes.
- Scannable hierarchy (clear H2/H3 flow).
- Short paragraphs and list formatting where helpful.
- Explicit conclusion with next-step links.

### Signs a page is too thin
- Mostly definitions with no action.
- Little to no workflow context.
- No criteria, no examples, no tradeoffs.
- Could be summarized in 5 generic bullet points.

### Signs a page is generic
- Reads like it could target anyone from startups to enterprises.
- Uses broad claims without audience constraints.
- Relies on cliché statements (“it depends”) without decision rules.

### Signs a page duplicates another page
- Same primary query intent as an existing page.
- Same workflow stage and same decision problem.
- No distinct audience, scenario, or outcome.

### Signs a page is search-engine-first, people-second
- Keyword variants repeated unnaturally.
- Headings built for volume terms, not reader flow.
- No clear recommendation or implementation section.
- Conclusion pushes clicks but not decisions.

## 3) Page-level standards by content type

## A) Practical guides

**Purpose:** Teach readers how to set up or improve a specific workflow component.

**Required sections:**
1. Who this guide is for
2. Problem this solves
3. Prerequisites
4. Step-by-step setup
5. Common mistakes and fixes
6. Minimal maintenance routine
7. Next-step links (workflow/comparison/template)

**Optional sections:** Time estimate, cost range, “fast-start” vs “advanced” variants.

**Intro should:** Match intent quickly and promise a concrete outcome.

**Conclusion should:** Confirm what’s now operational and direct the next action.

**Useful when:** Steps are specific, ordered, and constraint-aware.

**Weak when:** It gives philosophy, not implementation.

**Monetization fit later:** Contextual tool mentions where tools are genuinely required.

## B) Workflow pages

**Purpose:** Define end-to-end operating systems (inputs → stages → outputs).

**Required sections:**
1. Workflow scope and boundaries
2. Stage-by-stage map
3. Decisions required at each stage
4. Tool category options per stage
5. Failure points and controls
6. KPIs/checkpoints
7. Linked implementation resources

**Optional sections:** Role delegation notes, variant paths by business model.

**Intro should:** Explain why this workflow matters and what breaks without it.

**Conclusion should:** Recommend a baseline system and first implementation step.

**Useful when:** Readers can execute the full flow with minimal ambiguity.

**Weak when:** It lists steps without ownership, decisions, or outputs.

**Monetization fit later:** Limited; better as trust and linking infrastructure.

## C) Comparison pages

**Purpose:** Help users choose between options for a defined workflow job.

**Required sections:**
1. Comparison scope (“for X workflow, not all use-cases”)
2. Decision criteria
3. Side-by-side criteria analysis
4. Tradeoffs and constraints
5. Best-fit scenarios (“best for who”) 
6. Setup implications after choosing
7. Final recommendation by scenario

**Optional sections:** Migration notes, pricing evolution by stage.

**Intro should:** Define decision context and disqualify irrelevant readers early.

**Conclusion should:** Give scenario-based recommendation + setup link.

**Useful when:** It resolves a real decision with clear fit logic.

**Weak when:** It copies feature tables and avoids judgment.

**Monetization fit later:** Strong, but trust depends on honest tradeoffs and limits.

## D) Template/checklist pages

**Purpose:** Provide ready-to-use execution assets.

**Required sections:**
1. What this asset is for
2. When to use it
3. Copyable checklist/template body
4. How to adapt it quickly
5. Common customization mistakes
6. Companion links to full guides/workflows

**Optional sections:** Example filled-out version.

**Intro should:** State immediate utility and expected time to use.

**Conclusion should:** Route reader to full workflow context.

**Useful when:** Readers can apply it today without extra interpretation.

**Weak when:** Asset is generic and not tied to a workflow stage.

**Monetization fit later:** Email capture or low-ticket bundles after trust is established.

## E) Glossary pages

**Purpose:** Clarify terms used in workflow and setup content.

**Required sections:**
1. Plain-language definition
2. Why it matters in solo operations
3. Practical example
4. Related terms/pages

**Optional sections:** Common misconceptions.

**Intro should:** Define quickly with plain language.

**Conclusion should:** Push reader to applied pages.

**Useful when:** It improves comprehension in adjacent pages.

**Weak when:** It is dictionary content with no applied context.

**Monetization fit later:** Minimal direct; supports authority and user trust.

## F) FAQ pages

**Purpose:** Remove friction and objections that block implementation.

**Required sections:**
1. Audience-specific question set
2. Direct answer first
3. Brief rationale
4. Link to deeper page

**Optional sections:** “If you only do one thing” quick answer.

**Intro should:** Explain whose questions are answered and why.

**Conclusion should:** Route to a recommended starting page.

**Useful when:** Questions are specific and decision-blocking.

**Weak when:** It is keyword stuffing disguised as Q&A.

**Monetization fit later:** Indirect; improves conversion from core pages.

## 4) Search intent framework

## Informational intent
- **User wants:** Understanding of a concept or process.
- **Page type:** Guide, workflow intro, glossary.
- **Depth:** Medium; enough to drive action, not endless theory.
- **Mistakes:** Overexplaining basics without moving to implementation.

## Problem-solving intent
- **User wants:** Fix a specific operational pain now.
- **Page type:** Practical guide or troubleshooting FAQ.
- **Depth:** High and tactical (steps + checks + failure handling).
- **Mistakes:** Advice without diagnosis patterns.

## Comparison intent
- **User wants:** Confident choice between options.
- **Page type:** Comparison page.
- **Depth:** High on fit criteria and consequences.
- **Mistakes:** Fake neutrality, no recommendation.

## Selection intent
- **User wants:** Pick a stack/category/tool direction.
- **Page type:** Stack blueprint or decision framework guide.
- **Depth:** Medium-high with scenarios and constraints.
- **Mistakes:** Too many choices without narrowing logic.

## Implementation intent
- **User wants:** Execute setup quickly and correctly.
- **Page type:** Practical guide + template/checklist.
- **Depth:** High operational detail with sequence and quality checks.
- **Mistakes:** Generic “steps” with missing prerequisites or outcomes.

## 5) Writing style guide

### Sentence style
- Prefer direct, active voice.
- Average sentence length: short-to-medium.
- One idea per sentence when possible.

### Paragraph style
- 2–4 lines per paragraph.
- Lead with the key point, then explain.

### Clarity expectations
- Define terms on first use.
- State assumptions explicitly.
- Avoid hidden logic jumps.

### Reading level target
- Roughly Grade 7–9 readability while preserving professional credibility.

### Tone balance
- Practical + calm + decisive.
- Professional but not corporate.

### Jargon policy
- Minimal jargon.
- Use specialized terms only when they improve precision.
- Always pair jargon with plain-language meaning.

### Example usage rule
- Use examples whenever introducing a framework, decision rule, or abstract concept.
- Prefer solo-business scenarios over hypothetical enterprise cases.

### Heading rules
- Headings should state outcome or decision, not vague topic labels.
- Good: “Choose an all-in-one stack when…”
- Bad: “Stack considerations”

### List rules
- Use lists for steps, criteria, tradeoffs, and checklists.
- Keep list items parallel and specific.

### CTA language rules
- CTA must be utility-driven (“use this checklist next”).
- Avoid aggressive or vague sales phrasing.

### Preferred phrasing examples
- “Start with the minimum setup that can run reliably every week.”
- “Choose this option if you need speed over customization.”
- “If this step fails, check these three inputs first.”

### Phrasing to avoid
- “This revolutionary tool will transform your business overnight.”
- “There are many options and it depends.”
- “Click here to learn more.”

## 6) Comparison page methodology

### What a comparison must compare
- Two (or occasionally three) options for one clearly defined workflow job.
- Not full-platform universes; keep scope specific.

### Required criteria set
1. Workflow fit by stage
2. Setup time and complexity
3. Operational reliability for solo operators
4. Flexibility vs standardization tradeoff
5. Total practical cost (not just entry price)
6. Migration/switching friction
7. Team-scaling readiness (if relevant)

### How to frame differences
- Frame by scenario and constraint, not winner-takes-all language.
- Example: “Tool A fits fast onboarding pipelines; Tool B fits custom service ops with heavier setup.”

### How to avoid fake-objective language
- No “objectively best” claims.
- Declare assumptions and audience fit.
- Acknowledge where each option is weaker.

### “Best for” recommendation rules
- Must include explicit conditions (team size, budget, process complexity, growth horizon).
- Must include at least one “do not choose this if…” line for each option.

### How to avoid every comparison sounding the same
- Use a “decision core” unique to each workflow job (e.g., onboarding reliability vs delivery visibility).
- Require one custom criterion that is specific to that comparison context.
- Tailor examples to the relevant stage in the client lifecycle.

## 7) Workflow page methodology

### Definition
A workflow page is a pillar that documents how to run a complete operational process from trigger to completion, with clear decisions, tool roles, and quality controls.

### Step structure standard
For each workflow step, include:
1. Trigger/input
2. Goal/output
3. Owner (even if owner = solo operator)
4. Recommended tool category
5. Decision criteria
6. Common failure mode
7. Quality check

### How software categories should be introduced
- Introduce tools by category and role (CRM, PM, invoicing, automation).
- Mention specific tools only after role clarity is established.
- Keep tools subordinate to process design.

### How to prevent vagueness
- Require concrete outputs per stage.
- Require measurable checkpoints.
- Require at least one “minimum viable workflow” path.
- Ban generic stage names without deliverables.

### Required connections
- Link each stage to relevant setup guide(s).
- Link major tool decisions to comparison pages.
- Link execution steps to template/checklist assets.

## 8) Template/checklist page methodology

### What makes these pages useful
- They reduce execution time immediately.
- They prevent common omission errors.
- They are tied to a specific workflow stage.

### What should be included on-page
- Clear use-case statement.
- Copyable checklist/template content.
- Short adaptation instructions by scenario.
- “Before you use this” prerequisites.
- “After you use this” next step links.

### When a downloadable asset is justified
- When formatting or repeated use is important (weekly review, onboarding packet, audit sheets).
- When users benefit from offline/editable reuse.
- Not justified when a simple on-page checklist is sufficient.

### How much explanation is needed
- Enough to apply confidently in 5–15 minutes.
- Avoid long narrative blocks that delay action.

### How templates support the site
- Serve as conversion bridges from knowledge to action.
- Create recurring return visits.
- Reinforce authority by showing operational practicality.

## 9) Editorial differentiation rules

## Always do
- Always anchor content to a concrete workflow stage or decision.
- Always provide constraints and tradeoffs.
- Always include at least one practical next action.
- Always route readers to adjacent implementation resources.
- Always state who the guidance is for (and not for).

## Never do
- Never publish “best tools” pages without workflow context.
- Never write broad business trend commentary as core content.
- Never publish AI-generated drafts without human strategic rewriting.
- Never inflate lists to chase keyword breadth.
- Never let affiliate intent shape conclusions.

### Competitor contrast guardrails
- **Vs generic SaaS review sites:** We judge workflow fit, not features alone.
- **Vs broad business blogs:** We stay inside software-enabled operations only.
- **Vs AI content farms:** We prioritize specificity, judgment, and action pathways.

## 10) Content governance rules

### New topic admission rule
A topic earns its own page only if it has:
1. Distinct search intent,
2. Distinct workflow stage or decision,
3. Distinct user outcome,
4. Clear linking role in the architecture.

### When to merge topics
Merge when two pages share same intent + same stage + same outcome and only differ by minor keyword wording.

### When to expand an existing article instead of creating new page
Expand when added value is a sub-scenario, edge case, or supporting detail—not a distinct decision journey.

### Overlap prevention process
- Maintain a content inventory with fields: primary intent, stage, core query, canonical page, supporting pages.
- Run pre-brief overlap check before drafting.
- Enforce one canonical page per core decision topic.

### Consistency at scale
- Use standardized page templates by content type.
- Use a recurring editorial QA review cadence.
- Track and update “aging” pages with tool/workflow changes.
- Keep a style and terminology ledger to avoid drift.

## 11) Pre-publication checklist

Use this before publishing any page:

1. **Intent match:** Is the primary search intent explicit and satisfied?
2. **Usefulness:** Does the page produce a clear decision or action?
3. **Specificity:** Is audience + workflow stage clearly defined?
4. **Originality:** Does it contain unique framework/opinion/checklist value?
5. **Structure:** Are required sections present for this page type?
6. **Readability:** Is language clear, concise, and scannable?
7. **Internal links (inbound/outbound):** Does it connect correctly to hub/pillar/spoke assets?
8. **No overlap:** Is this page non-duplicative vs existing canonical content?
9. **Monetization restraint:** Are commercial elements contextual and non-dominant?
10. **Conclusion quality:** Does it give a specific next step?
11. **Trust check:** Are claims transparent and constraint-aware?
12. **Publish gate:** Would this still be valuable with all affiliate links removed?

If any critical item fails, do not publish.

## 12) Final Day 3 standards summary

- **Editorial mission:** Help solo operators build reliable, practical workflow systems with better software decisions and less operational friction.
- **Most important quality rule:** Every page must lead to a concrete decision or executable next step.
- **Biggest content trap to avoid:** Publishing high-volume, low-context comparison/list content that ignores workflow reality.
- **Strongest differentiation rule:** Recommendations must be scenario-based, constraint-aware, and linked to implementation paths.
- **Best Day 4 next step:** Create reusable content brief templates and QA scorecards for each page type, then apply them to the top 10 priority pages from Day 2.
