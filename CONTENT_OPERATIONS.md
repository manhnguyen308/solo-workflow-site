## Backlog structure

Use three backlog lanes only:

- `Now`: publish next because it strengthens an existing cornerstone page or closes a high-friction lifecycle gap
- `Next`: publish after the `Now` lane once the cluster path becomes more complete
- `Later`: useful but not urgent; publish only after current clusters are deeper

## Publishing priorities by content type

Use this order for the next stage of growth:

1. Workflow guides
Reason: highest authority-building value and strongest support for the current template/checklist pages.

2. Blueprint/decision-framework guides
Reason: strengthen stack clusters and improve comparison-page context.

3. Comparisons
Reason: useful growth lever, but only after the workflow or blueprint context is already strong enough.

4. Templates/checklists
Reason: publish new ones only when a real workflow page already exists or is clearly planned.

5. Glossary/FAQ support pages
Reason: use these to reduce friction inside existing clusters, not to inflate page count.

## Refresh and update rules

Use three review levels only.

### Level 1: cornerstone review

Review every 8-12 weeks:
- homepage
- all hubs
- workflow anchor
- solo freelancer stack blueprint
- CRM vs PM comparison
- onboarding checklist
- weekly operations checklist
- trust pages

Check for:
- weak intros
- stale reading paths
- missing links to newer support pages
- cluster gaps that make the page feel isolated

### Level 2: supporting-page review

Review every 12-16 weeks:
- supporting workflow guides
- migration guide
- other comparison pages
- high-traffic templates

Check for:
- overlap with newer pages
- weak next-step links
- sections that should be expanded or merged

### Level 3: support-page review

Review when a related cornerstone page changes or when term confusion appears in writing:
- glossary
- FAQ

Check for:
- whether the page still routes users clearly
- whether the page should be expanded, merged, or retired

## Deduplication rules

- If a new idea ends at the same decision as an existing page, expand the current page instead of publishing a new one.
- If a page would be useful only as a section inside a stronger existing page, do not split it out yet.
- If a support page stops routing readers to a stronger page, merge or rewrite it.

## Internal linking maintenance rules

Every new page must include:

- 1 upstream hub link
- 1 upstream cornerstone link
- 2 lateral related-page links where relevant
- 1 downstream next-step link

Before publishing, check:

1. Does the relevant hub mention this page if it is now important enough?
2. Does the relevant cornerstone page link to it if it solves a real subproblem?
3. Does the new page link back to the strongest page in the cluster?
4. Does at least one glossary, FAQ, template, or comparison page need updating because of it?

After every 3-5 new pages:

- run an orphan audit with `rg -n "<slug-or-title-fragment>" content`
- update affected hub pages
- update at least one cornerstone page in the same cluster

## Content pattern guidance

### Workflows

Use when the page explains a stage or sequence.

Must include:
- who the workflow is for
- what breaks without it
- stage/step logic
- inputs, outputs, or ownership
- common failure points
- exact next-step pages

### Blueprints and decision guides

Use when the page helps choose a stack shape or operating model.

Must include:
- assumed operating context
- what the page optimizes for
- overbuying warnings or tradeoffs
- upgrade triggers
- exact next comparison/workflow/template links

### Comparisons

Use only for one bounded decision.

Must include:
- what the reader is actually deciding
- criteria tied to workflow outcomes
- recommendation boundaries
- fit scenarios
- what page to open next after the choice

### Templates and checklists

Use only when the workflow rule is already defined.

Must include:
- trigger moment
- the asset itself
- common misses
- completion standard
- the workflow/guide page that gives the asset context

### Glossary and FAQ

Use as support only.

Must include:
- plain-language answer or definition
- why it matters operationally
- one clear next page

## Publishing workflow

Use this lightweight sequence:

1. Pick from the `Now` lane only.
2. Confirm the idea closes a real cluster gap.
3. Check whether expansion of an existing page is better than a new page.
4. Create the draft with the correct archetype.
5. Fill front matter before writing:
   - `description`
   - `summary`
   - `page_type`
   - `search_intent`
   - `page_role`
   - `related`
6. Write the page with the content pattern for its type.
7. Add upstream, lateral, and downstream links.
8. Update the hub and cornerstone page if the new page materially changes the cluster.
9. Build locally and review output.

## Practical publishing rhythm for a solo operator

Use a simple 6-page cycle:

- 2 workflow/supporting workflow pages
- 1 blueprint or decision-framework page
- 1 comparison page
- 1 template/checklist or glossary/FAQ support page
- 1 refresh/update pass on an existing cornerstone page

This keeps growth tied to the current structure instead of chasing breadth.
