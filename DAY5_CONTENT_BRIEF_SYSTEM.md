## 2) Brief-writing rules

### What makes a brief strong
- Defines one reader, one core problem, one primary decision/outcome.
- Contains explicit required sections tied to intent.
- Includes specific examples and “must include” proof elements.
- Names internal links before writing starts.

### What makes a brief weak
- Broad audience (“small business owners”).
- Vague goal (“help choose tools”).
- No decision criteria or workflow context.
- Generic outline that could fit any site.

### Specificity standard
A brief is publishable only if a writer can draft without guessing:
- who the reader is,
- what situation they are in,
- what decision/action they must finish,
- which linked pages must be referenced.

### Anti-generic SEO rules
- Never brief “best tools” without scenario boundaries.
- Never use features-only comparison criteria.
- Always tie tool choices to workflow stage and operator constraints.

### Overlap prevention
Before approving any brief, check:
- existing page with same primary intent,
- existing page with same decision endpoint,
- whether expansion of an existing page is better than a new page.

### Utility guarantee rule
Every brief must force at least one concrete output:
- chosen workflow model,
- chosen tool category/tool,
- completed checklist,
- implemented setup step.

## 4) Full brief for page 1

### Working title
Freelance Client Workflow System: Inquiry to Final Payment

### Page type
Workflow page

### Category
Client Workflow Systems

### Search intent
Problem-solving + implementation

### Page role
Primary workflow anchor page

### Target reader
Solo freelancer or consultant (0–3 collaborators) currently handling client work with ad hoc steps, missed handoffs, and inconsistent admin.

### Core problem
They do client work but lack a reliable end-to-end system; leads, onboarding, delivery, invoicing, and offboarding are disconnected.

### Page objective
Provide one clear end-to-end workflow model that the reader can adopt immediately and customize lightly.

### What this page must help the reader do
By the end, reader should map their current process to a 6-stage workflow and identify the next two implementation steps.

### Angle and differentiation
- Workflow-first sequence before tool talk.
- Focus on stage handoffs, failure points, and minimum viable controls.
- Recommend tool categories only where needed.

### Related pages this page supports
- How to Build a Client Intake and Qualification Workflow
- Proposal-to-Contract Handoff Workflow Setup
- Client Onboarding Checklist
- Invoice and Payment Workflow Checklist
- Client Offboarding + Testimonial Request Template

### Related pages this page should link to
- Software Stack Blueprint: Solo Freelancer (Lean Budget)
- CRM vs Project Management Tool for Client Workflows
- Glossary: Client Workflow Terms in Plain English
- FAQ: Setting Up a Solo Service Workflow Stack

### Required sections
1. Who this workflow is for / not for
2. Workflow map (6 stages)
3. Stage-by-stage breakdown (goal, inputs, output, owner, handoff)
4. Common failure points and fixes
5. Minimal software category map by stage
6. “First 7 days implementation” plan
7. Links to exact next-step guides/assets

### Optional sections
- Variation for project-based vs retainer work
- Variation for consultant + VA

### Proof/usefulness elements needed
- One full example client lifecycle walkthrough
- One “before vs after” process table
- One stage checklist summary block

### Examples to include
- Web designer handling one-off projects
- Consultant managing discovery-to-retainer progression

### Internal link targets
- Upstream: How to Choose a Software Stack Without Overbuying Tools
- Lateral: Solo Service Delivery Workflow Blueprint
- Downstream: Intake guide, onboarding checklist, payment checklist, offboarding template, key comparisons

### Monetization notes
No direct monetization focus in this page body. If any mentions exist, keep to neutral tool categories and link out to comparison pages for selection details.

### Risks to avoid
- Turning this into a tool list.
- Skipping handoff logic between stages.
- Being abstract without operational outputs.

### Completion standard
Page passes only if a new reader can implement stage order, identify required handoffs, and execute first-week setup steps using linked pages.

Primary decision node (high commercial intent)

They are choosing the wrong system-of-record, causing data fragmentation and missed follow-ups.

Help reader choose the right operating model based on workflow stage complexity and client volume.

- Compare operating models, not brand marketing claims.
- Show workflow consequences of each choice.

### Related pages this page supports
- Stack blueprint pages
- Migration guide
- Workflow anchor page

### Related pages this page should link to
- Notion vs ClickUp comparison
- Intake and onboarding guides

1. Decision context: what this comparison is (and is not)
2. CRM-first model: best for, tradeoffs, failure modes
3. PM-first model: best for, tradeoffs, failure modes
4. Hybrid model: best for, complexity warning
5. Criteria matrix (pipeline visibility, delivery tracking, admin overhead, scaling)
6. “Choose this if…” decision rules
7. Implementation next steps by chosen model

### Optional sections
- Migration trigger checklist
- Tool examples by model

### Proof/usefulness elements needed
- Criteria scoring framework
- Scenario-based recommendations (at least 3)
- “Wrong choice” warning signs table

- One-person consultant with low lead volume
- Agency-like solo operator with multiple concurrent projects
- Freelancer transitioning to retainer-heavy model

### Risks to avoid
- Feature checklist with no workflow context.
- Fake-objective “winner” language.
- Recommending hybrid model without complexity caveats.

### Completion standard
Reader can confidently choose one model and immediately navigate to a matching setup path.

## 9) Brief-to-page consistency controls

Use this gate before writing and again before publication:
1. **Intent lock check:** intro explicitly matches the brief’s primary intent.
2. **Reader lock check:** page speaks to one defined reader scenario.
3. **Outcome check:** page enables a concrete decision/action.
4. **Workflow-first check:** process and handoffs appear before tool recommendations.
5. **Distinctness check:** no overlap with existing page primary intent.
6. **Link-map check:** required upstream/lateral/downstream links are present.
7. **Monetization restraint check:** commercial mentions are contextual and secondary.

If any 2 checks fail, page returns to brief revision.

## 11) Risks in page briefing

- **Vague angle:** creates generic pages with no editorial edge.
- **Unclear reader:** writing becomes broad and low-conversion.
- **Missing page purpose:** content drifts into mixed intent.
- **Too many sections:** bloated article with weak clarity.
- **Generic intro:** fails to qualify user context and promise outcome.
- **Weak usefulness requirements:** no tables, steps, or decision rules.
- **Comparison briefs without decision logic:** become interchangeable “A vs B” filler.
